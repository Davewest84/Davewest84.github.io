Prompt caching — Claude Platform Docs

Prompt caching is a technique for cutting the cost and latency of talking to a large language model when much of what you send stays the same from one request to the next. The idea is simple. Instead of the model reprocessing your entire prompt every single time, you mark a stable prefix, and the system stores it. On later requests that share that prefix, the model resumes from the cached point rather than starting from scratch. Anthropic frames it as significantly reducing processing time and costs for repetitive tasks or prompts with consistent elements. In practice the things worth caching are the parts that don't change much, such as your system instructions, large background documents, and tool definitions.

There are two ways to set it up. Automatic caching means adding a single control field and letting the system place and move the cache point for you as a conversation grows, which suits multi-turn chat. Explicit breakpoints let you place up to four cache markers by hand when different sections of your prompt change at different rates. The key discipline is to put the marker on the last block that stays identical across requests. A common and costly mistake is putting it on something that changes every time, like a timestamp, which quietly causes a cache miss on every single call even though there's stable content sitting right behind it.

The economics are the interesting part. Reading from the cache costs a tenth of the normal input price. Writing to the cache costs slightly more than normal, at one and a quarter times the base rate for the standard five-minute cache, or double the base rate for a longer one-hour cache. So for anything you reuse repeatedly, the write premium is paid back many times over by the cheap reads. Concretely, on Opus 4.8, where base input is five dollars per million tokens, cache reads come in at fifty cents.

A few practical constraints are worth remembering. The default cache lives for only five minutes, refreshed each time it's used, so for slower agentic workflows you'll want the one-hour option. There's a minimum size below which nothing gets cached and no error is raised, and that floor varies by model, from around 500 tokens on the smallest up to a few thousand on the larger ones. Matching has to be exact, the lookback window is 20 blocks, and any change high up the stack, to your tools or system prompt, invalidates everything below it. As of February this year, caches are also isolated per workspace on several platforms rather than shared across a whole organisation.
